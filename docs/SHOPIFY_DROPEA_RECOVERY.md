## What it does

The dedicated worker scans every page of open, unfulfilled Shopify orders and checks the exact order reference against the complete Dropea store 16088 inventory. Existing references are never created again, including completed or cancelled Dropea orders. Native imports get a 30-minute grace period. Missing COD orders up to seven days old can be created only with an unambiguous SKU in the store's live linked catalog, sufficient stock, complete original mainland Spanish address and a live standard GLS 96|18 service. Older source orders without an exact reference are flagged for review; missing legacy references do not prove that no shipment ever existed. Other cases stay visible in the result for review. No postal-code substitution is allowed.

Discounted line amounts are distributed in integer cents, preserving exact units and the Shopify total. An odd cent may split one source line into two lines of the same variant. Non-representable shipping/extra charges, refunds, partial quantities, stale orders, blocked customers, non-COD orders and other destinations require review. For an absent COD email, the worker uses Dropea's existing technical routing convention (Spanish phone digits at the provider's dropea.io domain), verified on two native source/provider pairs. This is never represented as a customer's supplied email and never modifies Shopify customer data. The public API rejects blank emails even though the native Shopify importer generates this routing identifier.

Before the single creation POST, a persistent Supabase ledger claim uses `shopify_dropea_import_v1` and the Shopify order ID, and the source and Dropea are reread. The API receives a stable per-store/per-order/payload Idempotency-Key. A fresh GET and unique external-reference lookup verify reference, store, total, currency, payment method, variant quantities, contact and original address. A timeout or uncertain result remains claimed and cannot trigger a blind creation replay. A definitive HTTP 400 ValidationFailure with a subsequently changed payload can acquire a correction claim by conditional database update. The specific pre-saga POSTAL_CODE_NOT_COVERED rejection can also retry at most once per hour with an hourly key after conditional claim acquisition, so a provider coverage correction can recover without manual intervention. Uncertain outcomes, unchanged non-coverage rejections and attempts less than an hour old cannot retry. The operation endpoint can be polled when the provider returns its asynchronous operation ID. Missing or ambiguous dependencies fail closed. A paginated recent Dropea snapshot and paced reads avoid one API call per historical Shopify order; 429 responses back off and stop rather than flooding.

## Operation

Run `node autoconfirm/tools/recover-shopify-dropea.mjs` for a read-only audit, or target `--order-id=<Shopify numeric ID>`. Writes require both `--live` and `SULEIA_SHOPIFY_DROPEA_LIVE=true`. Use trusted runtime variables; never pass or log credentials as command arguments.

The enabled server timer runs at minute 05 of every even UTC hour (00, 02, through 22), every day, with persistent scheduling and a non-overlap file lock. This is every two hours in Europe/Madrid; the local clock label follows daylight saving time. It is independent of the operator's PC and does not replace the existing five-minute automation or half-hour incident timers. No Codex automation is required to run it. Historical Codex supervision never owns imports or starts duplicate cycles. `latest.json` records every scanned order and the precise blocking reason; `actions.jsonl` records attempted and verified/uncertain actions with order ID, reason and timestamps, without customer contacts. Both are private in `/var/lib/suleia-shopify-dropea`.

The deployment uses a dedicated immutable release under `/opt/suleia-shopify-dropea/releases/<commit>`, its own environment file, and the existing Node runtime. Copy only Shopify read credentials, Supabase ledger credentials and the existing Dropea read/create credentials to that protected environment; no Render management credential is needed on the server. Validate a read-only audit, the authorized canary and a second reconciliation before enabling the timer. The October 21 canary exercised provider rejection and zero-order postconditions; a successful real creation is not yet certified because Dropea rejects the original postal code. Do not describe that order as recovered until GET postconditions pass.
