## LIVE and capability release

Global LIVE enables memory/compiler observation; it cannot authorize a reply.
STATUS_REPLY and CONTEXTUAL_CLARIFICATION each require the reviewed benchmark,
fresh exact association and a durable capability admission in the existing
template_delivery_ledger. The administrative release identifier is metadata,
never a Dropea order or customer. The first naturally eligible exact case is
reserved atomically. A clarification canary must have exactly one missing fact.
Promotion is specific to its capability and requires one actual provider POST,
a WAMID receipt, transcript readback and the immediately-before-dispatch guard.
An uncertain canary cannot be replayed. A proven zero-POST abort may release
the capability to another eligible natural case; its message claim is retained.

The final reads reserve the existing serialized Chatby queue. Fresh native
order/issue, subscriber and full transcript are compared with the compiled
plan, current ownership, memory and release switches. No unrelated queue item
may intervene before the single POST. Read failures, 429, expired evidence,
later/edited inbound messages and changed provider amounts block dispatch.
After sending, transcript evidence also detects duplicate WAMIDs, wrong
receipt recipients and a confirmed pre-dispatch inbound omitted by the read.

Only one active question is permitted per order/issue. Its durable receipt
keeps subsequent cycles at WAITING_CUSTOMER with SEND=0 until a later inbound.
Operational delegation consumes the branded compiled context and the current
provider action contract through the existing claim/writer; V3 is not a
second operational owner. Partial dates/windows never widen a stated window.

## Amount and payment

Payment is informational, never a request to confirm cash availability.
Any quoted amount requires a consistent fresh native EUR/COD total. Accepted
discount intent routes to the existing accepted-discount owner before payment
questions. A final discounted quote additionally requires that owner's verified
receipt, exact order/conversation and a fresh current total equal to its final
amount. A support email or a solution request alone is not proof of application.
The existing amount notice likewise waits for a fresh final total. No offer,
discount amount, timer or return-after-offer policy is changed.

## Monitoring and reply rollback

The existing cycle report records actual V3 sends, clarifications, delegations,
verified actions, stale-plan blocks, unknown writes, rate-limit failures and
P0 evidence. Durable memory retains question receipts, superseded facts and
logistics follow-up. Semantic/external models stay disabled at 0 USD.

A confirmed duplicate, recipient/order/owner/irreversible-route error, blind
retry or stale-plan write persists a P0 breaker in the same ledger. Both reply
capabilities then fail closed at admission and final dispatch; memory and
legacy continue. Configured switches and this effective breaker are reported
separately. Do not delete claims, journals or case memory to clear a problem.

For an operator rollback, set only conversationV3.clarification/statusReply
false in the existing control, leave memory enabled, then restore the saved
V3 image/control or Render revision when necessary. Preserve every unrelated
control and all post-activation state. Encrypted pre-activation backup, source
hash manifest, deployment receipts and exact rollback commands are retained
privately on the VPS; secrets and customer histories are not repository files.
